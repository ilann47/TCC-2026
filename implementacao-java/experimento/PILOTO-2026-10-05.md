# Conferência do piloto — 05/10/2026

**Finalidade:** verificar se os instrumentos conseguem correlacionar cada evento entre k6, resposta HTTP, marco de commit e PostgreSQL. Não calibrar a capacidade do sistema nem confirmar hipóteses de desempenho/resiliência.

## Execução conferida

Ambiente local Windows/WSL, Docker Engine/CLI `29.1.3`, Compose `2.40.3+ds1-0ubuntu1`, k6 `2.3.0` com digest fixado no executor. As aplicações existentes usam os limites de Compose: 1 CPU/512 MiB para cada API, consumidor e PostgreSQL; 1 CPU/1 GiB para Kafka. O manifesto local registra IDs das imagens e configurações. Não houve exclusão de registros ou volumes.

Cada variante foi executada uma vez com `RATE=2`, `DURATION=10s`, `VUS=4` e `DRAIN_SECONDS=5`. O resumo considera a **quantidade efetivamente observada**, não uma quantidade presumida a partir da taxa e duração. As consultas de saúde ficam fora das amostras dos eventos no analisador.

## Tentativas inválidas e diagnóstico

Não foram selecionadas apenas execuções bem-sucedidas. Estas tentativas ficaram preservadas e marcadas como inválidas porque não foi possível conciliar os marcos de commit pela leitura normal dos logs:

| UUID | Variante | Eventos / registros conferidos | Commits conciliados no coletor |
|---|---|---:|---:|
| `3c8ba9d2-ba6f-4f5c-b9a2-4b1a447f018c` | Síncrona | 20 / 20 | 0 |
| `70ed6562-368b-476a-98f9-0726e5cca1c5` | Síncrona | 21 / 21 | 0 |
| `6ca09707-6642-47b2-a2db-9b5aa8ab7196` | Síncrona, diagnóstico de 2 s | 5 / 5 | 0 |
| `eb17607e-f76f-48b4-af30-6d44456e694d` | Síncrona | 21 / 21 | 0 |
| `b8a2fab0-b735-4fd7-9a6e-0b11fd9e8b89` | Assíncrona | 21 / 21 | 0 |

Houve também uma interrupção na checagem inicial de serviços, **antes de enviar eventos**, quando PostgreSQL/Kafka estavam parados. Após cada sessão não persistente de WSL, foi observado encerramento dos serviços; a execução final manteve uma sessão de WSL ativa. A causa dessa configuração de ciclo de vida do ambiente não foi alterada.

O arquivo antigo de log da API síncrona continha **2.595 bytes nulos**. Uma leitura direta encontrou o UUID `eb17607e-f76f-48b4-af30-6d44456e694d` no arquivo, embora a consulta normal de logs não o entregasse ao coletor. Isso é uma falha da evidência coletada, **não evidência de perda de registros**: os conteúdos das linhas no banco foram conferidos em todas as tentativas.

Foram guardadas cópias dos logs antigos das três aplicações em `.runtime/docker-log-recovery-2026-10-05/`, e recriados **somente** os contêineres `sync-api`, `async-api` e `consumer`. PostgreSQL, Kafka e seus volumes foram preservados. A leitura dos logs passou a funcionar nas duas execuções finais. O coletor agora filtra marcos pelo UUID, sem depender de `--since`; essa mudança, sozinha, não resolveu os arquivos antigos inválidos. Não houve alteração do código das aplicações para contornar o problema.
