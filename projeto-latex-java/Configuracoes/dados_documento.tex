\textoresumo{Este trabalho compara experimentalmente duas implementações Java de processamento de registros de auditoria: uma API REST síncrona e uma solução assíncrona com Apache Kafka e consumidor. As variantes compartilham contrato, validação, hash e persistência em PostgreSQL. Após calibração e nove validações do piloto R2, uma campanha local com k6 observou 65 UUIDs em treze condições e cinco tentativas por condição, incluindo cargas constantes, rajada e indisponibilidades. Houve 64 coletas completas e uma parcial qualificada por emenda analítica, preservando o veredito original e sem imputar um instante de commit ausente. A análise descritiva por execução e par separa resposta HTTP, conclusão, vazão, recursos e destinos. A assíncrona apresentou menor p95 de aceite e maior uso de CPU/memória nos pares comparáveis, mas maior p95 de conclusão nas condições sem falha. Com consumidor parado, todos os aceites foram persistidos ao fim; com banco parado, 14 eventos aceitos terminaram em fila de falhas terminais e somente uma de cinco execuções assíncronas satisfez o critério de recuperação sustentada na janela ativa. Os resultados sustentam compromissos contextuais, não superioridade geral. Um computador compartilhado, broker único, dados sintéticos, cinco tentativas e a emenda pós-hoc limitam a generalização.}

\textoabstract{This work experimentally compares two Java implementations of audit record processing: a synchronous REST API and an asynchronous solution using Apache Kafka and a consumer. Both share the data contract, validation, hashing, and PostgreSQL persistence. Following calibration and nine R2 pilot validations, a local k6 campaign observed 65 planned run identifiers across thirteen conditions with five attempts each, including constant loads, a burst, and outages. There were 64 complete collections and one qualified partial collection under an analytical amendment, preserving the original verdict without imputing a missing commit timestamp. Descriptive run-level and matched-pair analysis separates HTTP response, completion, throughput, resources, and event destinations. The asynchronous variant had lower acceptance p95 and higher CPU/memory usage in comparable pairs, but higher completion p95 in non-failure conditions. All accepted events were eventually stored after consumer outages; during database outages, 14 accepted events reached the dead-letter queue and only one of five asynchronous runs met the sustained recovery criterion within active input. The results support contextual trade-offs rather than general superiority. A shared computer, a single broker, synthetic data, five attempts, and the post-hoc amendment limit generalization.}
