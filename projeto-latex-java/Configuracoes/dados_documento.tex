\textoresumo{Este trabalho compara duas implementações Java para processar registros de auditoria: uma API REST síncrona, que confirma a gravação antes de responder, e uma API assíncrona com Apache Kafka, que confirma a publicação e deixa a gravação para um consumidor. As variantes compartilham contrato, validação, hash e armazenamento em PostgreSQL. Após calibração e validação dos instrumentos, foram realizadas 65 coletas, em treze condições com cinco repetições, incluindo cargas constantes, rajada e indisponibilidades controladas. A análise descritiva utiliza cada coleta e cada par de conteúdo equivalente como unidades de comparação. Na carga de 48 eventos por segundo, as médias dos percentis 95 de resposta HTTP foram 2,60 ms na assíncrona e 4,34 ms na síncrona; para conclusão da gravação, foram 5,83 ms e 3,92 ms, respectivamente. Na carga de 12 eventos por segundo, a assíncrona utilizou aproximadamente duas vezes a CPU e quatro vezes a memória do caminho síncrono. Com o consumidor parado, todos os eventos aceitos foram gravados ao fim da observação; com o banco parado, 14 eventos aceitos terminaram na fila de falhas, sem gravação automática posterior. Uma coleta apresentou evidência temporal incompleta: um registro foi gravado apesar da resposta de erro, mas seu instante de conclusão não foi registrado. Essa coleta foi preservada sem repetição ou estimativa do tempo ausente, e a comparação de conclusão afetada utilizou quatro pares completos. Os resultados indicam que aceitar mais rapidamente não significa concluir mais cedo: a escolha depende da necessidade de confirmação, do uso de recursos e do tratamento de falhas. O ambiente local compartilhado, as cinco repetições e a revisão analítica posterior limitam a generalização.}

\textoabstract{This study compares two Java implementations for processing audit records: a synchronous REST API, which confirms database storage before responding, and an asynchronous API using Apache Kafka, which acknowledges publication and delegates storage to a consumer. Both variants share the data contract, validation, hashing, and PostgreSQL storage. Following calibration and instrument validation, 65 runs were performed across thirteen conditions with five repetitions, including constant loads, a burst, and controlled outages. Descriptive analysis uses each run and each matched pair with equivalent contents as comparison units. At 48 events per second, the mean run-level 95th percentiles of HTTP response time were 2.60 ms for the asynchronous variant and 4.34 ms for the synchronous variant; completion values were 5.83 ms and 3.92 ms, respectively. At 12 events per second, the asynchronous path used approximately twice the CPU and four times the memory. After consumer outages, all accepted events were stored by the end of observation; during database outages, 14 accepted events reached the dead-letter queue without automatic subsequent storage. One run had incomplete timing evidence: a record was stored despite an error response, but its completion timestamp was not recorded. That run was preserved without repetition or timestamp estimation, and the affected completion comparison used four complete pairs. The results show that faster acceptance does not mean earlier completion: selection depends on confirmation requirements, resource use, and failure handling. The shared local environment, five repetitions, and post-hoc analytical revision limit generalization.}
